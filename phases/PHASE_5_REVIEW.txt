1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
Phase 5 equips SupportFlow with production-grade, explainable operational intelligence.
Without black-box models or third-party AI dependencies, it delivers deterministic,
transparent, real-time guidance directly computed from live database transactions:

1. Urgency Ranking & Attention Score Engine:
   - Attention Score (0–100) dynamically synthesized from four explainable factors:
     * Priority Base Weight: P1 (40 pts), P2 (25 pts), P3 (15 pts), P4 (5 pts).
     * Customer Waiting Time: Hours elapsed without staff response scaled up to 25 pts.
     * Remaining SLA Time & Pressure: Breached commitments (+30 pts), critical upcoming
       deadlines <1h (+20 pts), <4h (+12 pts), on track (+3 pts).
     * Assignment State: Unassigned tickets requiring triage receive an attention boost (+15 pts).
   - Strict Separation: The original ticket priority (P1–P4) is maintained strictly separate
     from the calculated attention score in both MongoDB schemas and UI representations.
   - Explainability: Every score returns a structured factor breakdown and plain-English narrative.

2. Workload-Aware Agent Recommendations:
   - Matches tickets to the best-suited active staff members using three clear dimensions:
     * Expertise Factor (0–40 pts): Match against agent's designated category skills and historical
       resolution volume within that category.
     * Workload Bandwidth Factor (0–40 pts): Real-time aggregation of active tickets (open, in_progress)
       measured against agent maximum capacity (idle=40 pts, light load=35 pts, moderate=20-28 pts, at capacity=0 pts).
     * Availability Factor (0–20 pts): Eligibility based on active duty status (isActive: true).
   - Explainability: Full factor scores, utilization percentages, and human-readable explanation
     provided for every candidate agent. Leads and Admins can assign directly from recommendations.

3. Recurring-Issue Detection & Incident Clustering:
   - Employs deterministic text normalization and Jaccard token similarity (|A ∩ B| / |A ∪ B|)
     partitioned across structured categories ('technical', 'billing', 'bug', etc.).
   - Incident Cluster Hygiene:
     * Potential Incident Classification: Every cluster with ≥2 correlated tickets is classified
       as a Potential Incident requiring human review.
     * Strict Causality Disclaimer: Does not claim that text similarity proves tickets share a root cause.
       Explicitly states that text overlap flags correlated symptoms and wording, requiring manual technical
       verification before declaring a shared defect or outage.
   - Non-LLM Architecture Justification:
     * Cost: Zero token fees, zero third-party API costs, and zero GPU infrastructure overhead.
     * Privacy: Full data sovereignty — customer tickets and PII never leave the tenant database.
     * Failure Handling: 100% offline uptime, zero network latency, and no third-party rate-limiting.
     * Explainability: Transparent shared keyword tokens explain exactly why tickets were clustered.

4. Bottleneck Analytics Radar:
   - High-performance MongoDB aggregations analyzing 5 operational bottleneck dimensions:
     * Unassigned Tickets: Total count, average/max triage waiting hours, priority breakdown, oldest items.
     * Tickets Waiting for Customers: Count in 'pending' status, average pending hours, and stale tickets (>72h).
     * Tickets Awaiting Engineering: Software bugs, explicit engineering flags, and active technical queries.
     * SLA Breaches: Real-time count of first-response vs resolution breaches, broken down by priority and agent.
     * Workload Imbalance: Computes mean active tickets (μ), variance, standard deviation (σ), and max/min
       imbalance ratio, automatically classifying workload state ('balanced', 'moderate_imbalance', 'severe_imbalance')
       and identifying overloaded vs underutilized agents with actionable rebalancing advice.

Verification Metrics:

- Clean TypeScript verification with zero errors across backend and frontend (`npm run typecheck`).
- Production bundles built cleanly with zero errors (`npm run build`).

2. WORKFLOW FROM FRONTEND TO EXPRESS API TO SERVICE TO MONGODB AND BACK
--------------------------------------------------------------------------------

A. URGENCY RANKING & ATTENTION SCORING:
   1. Frontend (`OperationalIntelligenceTab` or `AgentDashboardPage`) queries `GET /api/operations/urgency-ranking`.
   2. Auth Middleware verifies JWT and staff role (`agent`, `lead`, `admin`).
   3. Service Layer (`urgencyRanking.service.ts`):
      - Fetches active tickets scoped strictly to `workspaceId`.
      - Computes `calculateWaitingTimeScore()`, `calculateSLAPressureScore()`, and `calculateAssignmentScore()`.
      - Combines factors into `attentionScore` (0-100) and assigns `urgencyTier` ('critical', 'high', 'medium', 'low').
      - Compiles structured `factors` array and human-readable `explanation`.
      - Sorts tickets by `attentionScore` descending while preserving `originalPriority` untouched.
   4. Frontend renders `AttentionScoreBadge` alongside `PriorityBadge` with interactive explanation popovers.

B. WORKLOAD-AWARE AGENT RECOMMENDATIONS:
   1. User opens a ticket (`/agent/tickets/:id`) or clicks "Match Agent" in the Urgency Queue.
   2. Frontend calls `GET /api/operations/recommendations/:ticketId`.
   3. Service Layer (`agentRecommendation.service.ts`):
      - Reads ticket category and priority from MongoDB.
      - Finds all active workspace staff (`role: { $in: ['agent', 'lead'] }, isActive: true`).
      - Runs MongoDB aggregation for active ticket counts per agent.
      - Runs MongoDB aggregation for historical resolved tickets per agent in this category.
      - Computes expertise, workload bandwidth, and availability scores for each candidate.
      - Ranks candidates by `matchScore` descending and flags the top match with `isRecommended = true`.
   4. Leads and Admins click "Assign to Agent", triggering `PATCH /api/tickets/:id/assign`,
      broadcasting real-time Socket.IO events and dispatching in-app notifications.

C. RECURRING-ISSUE DETECTION & CLUSTERING:
   1. Frontend queries `GET /api/operations/recurring-issues?daysLookback=30`.
   2. Service Layer (`clustering.service.ts`):
      - Queries recent tickets matching tenant `workspaceId`.
      - Groups tickets by structured category (`technical`, `billing`, `bug`, etc.).
      - Tokenizes text (subject + description), stripping stop words, numbers, and short terms.
      - Calculates pairwise Jaccard token similarity |A ∩ B| / |A ∪ B|.
      - Forms connected components for pairs exceeding the similarity threshold.
      - Filters out singletons (retains clusters with ≥2 tickets).
      - Extracts top shared keywords, first/last seen timestamps, and average similarity.
      - Enforces the non-causality disclaimer: "Potential incident requiring human review. Text similarity
        indicates correlated patterns, not proven shared cause."
   3. Frontend renders interactive cluster cards with shared keyword pills, correlated ticket lists,
      and non-LLM methodology transparency.

D. BOTTLENECK RADAR ANALYTICS:
   1. Frontend queries `GET /api/operations/bottlenecks`.
   2. Service Layer (`bottleneckAnalytics.service.ts`):
      - Executes parallel aggregation pipelines across the 5 operational dimensions.
      - Calculates mathematical workload variance: mean μ = T / N, standard deviation σ = sqrt(Σ(x - μ)² / N).
      - Classifies balance status and pinpoints overloaded/underutilized personnel.
   3. Frontend renders radar dashboard with real-time StatCards, breakdown tables, and rebalancing guidance.

4. CODE CLEANLINESS, DEPENDENCY & SECURITY AUDIT
--------------------------------------------------------------------------------
1. Zero Black-Box LLM / Embedding Overhead:
   - Evaluated against user instructions: No LLM, vectors, or third-party embeddings introduced.
   - Cost: $0 API token expense.
   - Privacy: Zero PII leaves the local MongoDB database.
   - Failure Handling: Zero network dependency on external AI model APIs; 100% deterministic and offline-capable.
   - Simpler Alternative: Category-partitioned token normalization + Jaccard similarity provides fully
     explainable, auditable keyword matching.
2. Tenant Isolation:
   - Every operational query strictly enforces `workspaceId: req.user.workspaceId`.
   - Verified in automated tests: Workspace B tickets are never included in Workspace A's
     urgency rankings, bottleneck analytics, or agent recommendations.
3. Priority Preservation:
   - Original ticket priority (`P1`, `P2`, `P3`, `P4`) is untouched and strictly separate from
     the operational attention score (0-100).
4. Incident Cluster Responsibility:
   - Issue clusters explicitly carry the disclaimer that text similarity indicates correlated
     patterns rather than confirmed shared root cause, avoiding false automation claims.
