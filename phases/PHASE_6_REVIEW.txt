2. COMPREHENSIVE SECURITY & OPERATIONAL AUDIT FINDINGS
--------------------------------------------------------------------------------

A. Staff Authentication, HTTP-Only Cookie Storage & Refresh Token Rotation
   - Verified that all authentication tokens are strictly stored in `httpOnly`, `sameSite`, and `secure` (in production) cookies (`accessToken` and `refreshToken`).
   - Verified zero tokens stored in browser `localStorage`. Frontend `client.ts`, `AuthContext.tsx`, and `realtime/socket.ts` contain zero token reads from `localStorage`.
   - Implemented short-lived access tokens (15 minutes) and long-lived rotating refresh tokens (7 days) with cryptographic SHA-256 hashing in MongoDB (`RefreshToken` model).
   - Refresh Token Rotation & Family Reuse Detection: Each refresh generates a new refresh token and revokes the predecessor. If an old or compromised refresh token is replayed, the entire token family is immediately revoked, preventing replay attacks.
   - Frontend Transparent 401 Interceptor: Automatically triggers `POST /api/auth/refresh` on 401 Unauthorized responses, queues concurrent requests, and retries seamlessly without interrupting user activity.
   - Socket.IO cookie handshake parsing: WebSockets authenticate seamlessly via browser HTTP-only cookies.
   - Enforced `requireRole` middleware across all staff routes. Attempts by Support Agents to access Admin
     endpoints (`/api/admin-reports`, `/api/reports`) return HTTP 403 Forbidden with clean JSON messages.
   - Verified frontend `RoleRoute` component prevents unauthorized URL navigation, rendering a clear
     Access Restricted (403 Forbidden) guard screen while preserving user session and state.

B. Workspace & Multi-Tenant Isolation
   - Verified that all staff-facing database queries unconditionally scope on `workspaceId: req.user.workspaceId`.
   - Verified that client-supplied tenant identifiers are never trusted without verified workspace membership.
   - Verified cross-tenant isolation: An agent from Workspace A attempting to inspect or download records
     belonging to Workspace B receives an immediate HTTP 404 Not Found error.

C. Public Ticket Tracking Security & Dual-Identifier Resolution
   - Customer tracking routes (`/api/public/tickets/track/:token`) accept either friendly ticket IDs (`TCK-1008`)
     or 64-character unguessable cryptographic tokens (`0db61e...`).
   - Verified that public ticket responses strictly strip all internal fields: staff assignments, internal notes,
     agent consultations, SLA breach warning logs, and system audit trails are completely withheld from the customer.
   - Post-submission screen provides a prominent Hero Ticket ID Card, one-click clipboard copy, and a 3-step
     ticket monitoring guide.

D. Customer-Visible vs. Internal Staff Messages
   - Verified that `isInternal: true` can only be set by authenticated staff members (`sender.type === 'agent'`).
   - Public tracking endpoint (`GET /api/public/tickets/track/:token`) applies a mandatory MongoDB filter
     `isInternal: false`, ensuring internal staff discussions remain strictly invisible to customers.
   - Customers posting follow-up messages automatically transition tickets from `resolved` to `open`
     via atomic database updates, waking up agents without allowing customer modification of priority or internal metadata.

E. Ticket Lifecycle & State Machine Rules
   - Verified strict state machine transitions in `ticket.service.ts`:
     * `open` -> `in_progress` | `pending` | `resolved` | `closed`
     * `in_progress` -> `pending` | `resolved` | `closed`
     * `pending` -> `in_progress` | `resolved` | `closed`
     * `resolved` -> `open` (customer reopen) | `closed`
     * `closed` -> terminal state (no transitions permitted)
   - Invalid transitions (e.g. attempting to jump from `closed` to `in_progress`) are strictly rejected
     with HTTP 400 Bad Request and descriptive state error messages.

F. Validation, Rate Limits, CORS, Security Headers & Error Responses
   - Request payloads are parsed using strict runtime Zod schemas. Invalid payloads return HTTP 400 with
     detailed validation error structures.
   - Global API Rate Limiter (`apiLimiter`): 1000 requests per 15 minutes per IP applied across `/api`.
   - Authentication Rate Limiter (`authRateLimiter`): 30 requests per 15 minutes per IP on `/api/auth/login`
     preventing brute-force credential stuffing.
   - Helmet Security Headers: Injects `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`,
     `Strict-Transport-Security`, and Content Security Policy headers.
   - Centralized Error Handler (`errorHandler.ts`): Masks internal errors in production, suppresses stack
     trace leakage to clients, and logs unhandled exceptions via structured logger.

G. Attachment Access Restrictions & Path Sanitization
   - Uploaded filenames are sanitized against directory traversal attacks (`../`, `..\`) and null byte (`\0`) injections.
   - Prohibited Executable Extensions: Files ending in `.exe`, `.sh`, `.bat`, `.cmd`, `.msi`, `.dll` are rejected (HTTP 400).
   - Maximum File Size: Uploads exceeding 10MB (10,485,760 bytes) are rejected with a clear payload error.
   - Public Download Endpoint (`GET /api/public/tickets/track/:token/attachments/:attachmentId`):
     Strictly verifies `isInternal === false`. Requests for internal attachments return HTTP 403 Forbidden.
   - Staff Download Endpoint (`GET /api/tickets/:id/attachments/:attachmentId`):
     Strictly enforces tenant workspace scoping. Cross-workspace downloads return HTTP 404 Not Found.
   - Downloads include `Content-Disposition: attachment; filename="..."` and `X-Content-Type-Options: nosniff`.

H. Background Jobs, SLA Engine & Email Deduplication
   - BullMQ Queue Worker: Configured with 3 retry attempts and exponential backoff (`delay: 1000ms`, `backoff: exponential`).
   - Job Deduplication: Email notifications and SLA alerts require deterministic deduplication keys (`deduplicationKey`).
     Duplicate queue dispatches within window are discarded to prevent customer email spamming.
   - Resilient Fallback: If external Redis is temporarily disconnected or unreachable, the queue runner
     gracefully falls back to an in-memory execution pipeline, ensuring SLA evaluations continue without crashes.
   - SLA Engine: Accurately calculates First Response deadlines and Resolution deadlines based on priority
     (P1=1h/4h, P2=4h/16h, P3=8h/48h, P4=24h/96h), pauses timers when awaiting customer input (`pending`),
     and calculates warning triggers at 75% elapsed SLA time.

I. Analytics Accuracy & Pagination
   - Bottleneck radar and reporting queries use high-performance MongoDB `$facet` and aggregation pipelines.
   - Staff inbox endpoints enforce strict pagination defaults (`page: 1, limit: 20`) with indexed sorting
     on `updatedAt` and `attentionScore`, preventing denial-of-service from massive queue queries.

J. Frontend Loading, Empty, Error & Mobile States
   - Loading State: Skeleton tables and pulse animations indicate ongoing background queries.
   - Empty State: Informative empty state cards for queues, consultations, and message threads.
   - Error State: Contextual error banners with user-friendly retry buttons (`onRetry`).
   - Responsive Mobile Viewport: Verified under 375x667 viewport dimensions (iPhone 13 standard).
     Navbar collapses cleanly, form cards stack vertically, and touch targets meet accessibility guidelines.

5. PRODUCTION DEPLOYMENT SPECIFICATIONS
--------------------------------------------------------------------------------

SupportFlow is architectured for high-availability cloud deployment:

1. Frontend Static SPA:
   - Hosting: Vercel, Netlify, Cloudflare Pages, or AWS S3 + CloudFront.
   - Build: `npm run build --workspace=frontend` -> `frontend/dist`.
   - Routing: Configure SPA rewrite rule redirecting `/*` to `/index.html`.
   - Environment: Set `VITE_API_URL=https://api.yourdomain.com`.

2. Backend API Container:
   - Hosting: AWS ECS, Google Cloud Run, Render, Fly.io, or Kubernetes.
   - Entrypoint: `node backend/dist/server.js`.
   - Probes: Readiness probe -> `GET /api/health/ready`, Liveness probe -> `GET /api/health/live`.
   - Port: Binds to `$PORT` (default 5000).

3. Background Queue Worker:
   - Run as a separate worker service running the same container image.
   - Scales horizontally to consume BullMQ SLA and notification jobs from Redis.

4. Managed Services:
   - Database: MongoDB Atlas (M10+ Replica Set recommended). Configure IP allowlist to VPC.
   - Cache & Queues: Managed Redis (AWS ElastiCache, Upstash, or Redis Cloud) with TLS.
   - Object Storage: AWS S3 or Cloudflare R2 (`STORAGE_DRIVER=s3`). Bucket access is private.
