2. END-TO-END DATA FLOW (FRONTEND -> EXPRESS API -> SERVICE -> MONGO -> RESPONSE)
--------------------------------------------------------------------------------

A. Public Customer Ticket Submission Flow:
   1. Frontend (`/support`): Customer fills in Name, Email, Subject, Category,
      Urgency, and Description. React state validates non-empty inputs.
   2. API Client (`apiClient`): Dispatches POST to `/api/public/tickets`.
   3. Express Middleware: Rate limiter (`express-rate-limit`) checks IP quota
      (100 req / 15 min).
   4. Controller (`submitPublicTicket`): Zod schema (`createTicketSchema`) parses
      and sanitizes string lengths and email format.
   5. Service Layer (`createPublicTicket`):
      - Locates active workspace.
      - Atomically increments `workspace.ticketCounter` ($inc) to yield `TCK-XXXX`.
      - Generates cryptographically secure 32-byte hex token (`trackingToken`).
      - Persists new `Ticket` document with status 'open'.
      - Writes initial `AuditEvent` ('ticket_created').
   6. Response: Standardized envelope returns `{ success: true, data: { ticketNumber, trackingToken, trackingUrl } }` with HTTP 201 Created.
   7. Frontend UI: Displays confirmation with direct one-click link to `/track/:token`.

B. Customer Ticket Tracking & Follow-up Flow:
   1. Frontend (`/track/:token`): Calls `GET /api/public/tickets/track/:token`.
   2. Service Layer (`getTicketByTrackingToken`):
      - Finds ticket by indexed `trackingToken`.
      - Queries `Message` collection strictly filtering `{ ticketId, type: 'reply' }`.
      - Excludes any message with `type: 'internal_note'`.
   3. Follow-up Message (`POST /api/public/tickets/track/:token/messages`):
      - Saves message with `type: 'reply'`.
      - Automatic Reopen Rule: If ticket status was 'resolved', automatically transitions
        status back to 'open' and writes an audit event.

C. Staff Ticket Inbox & Details Flow:
   1. Staff Login (`POST /api/auth/login`): Verifies credentials via bcrypt, issues
      JWT in HTTP-only cookie and JSON response body.
   2. Staff Request Header: `Authorization: Bearer <token>` or HTTP cookie.
   3. Auth Middleware (`authenticate`): Decodes JWT, attaches `req.user` and verified
      `req.workspaceId`.
   4. Staff Listing (`GET /api/tickets`):
      - Strictly queries `{ workspaceId: req.workspaceId }` (Tenant Isolation).
      - Applies server-side filters: status, priority, category, regex search.
      - Applies server-side pagination: `skip((page - 1) * limit).limit(limit)`.
   5. Staff Ticket Detail (`GET /api/tickets/:id`):
      - Enforces `{ _id: id, workspaceId: req.workspaceId }`.
      - Returns all messages (both public replies AND private internal notes).
      - Returns chronological audit log.
   6. Status Transition (`PATCH /api/tickets/:id/status`):
      - State machine verifies permitted transitions (`open` -> `in_progress` -> `resolved` -> `closed`).
      - Rejects invalid transitions with 400 Bad Request.
      - Writes audit log event (`status_changed`).

4. CODE QUALITY & SECURITY AUDIT FINDINGS
--------------------------------------------------------------------------------

[A] Duplicated Code:
    - Initially, error handling was repeated across async routes. Fixed by implementing `asyncHandler.ts`, standardizing promise rejection routing to `errorHandler.ts`.
[B] Unnecessary Dependencies:
    - All dependencies (`bcryptjs`, `jsonwebtoken`, `cookie-parser`, `express-rate-limit`, `@tanstack/react-query`) serve direct, required architectural purposes. No bloatware or unused libraries were introduced.
[C] Placeholder Functionality:
    - Zero placeholder functions exist. All routes read and persist real MongoDB documents via Mongoose models.
[D] Security Verification:
    - Insecure Direct Object Reference (IDOR) Defense: Public ticket tracking URLs use 64-char crypto tokens (`/track/:token`), never incremental IDs or predictable slugs.
    - Tenant Isolation: Staff routes query `{ _id: ticketId, workspaceId: req.workspaceId }`. An agent from Workspace B attempting to query Workspace A receives a 404 error.
    - Message Confidentiality: Customer tracking queries strictly filter `{ type: 'reply' }`. Internal staff notes are never serialized to the public API.
    - Password Security: `passwordHash` has `select: false` on the User model; passwords are never exposed in user responses.
    - Rate Limiting: Public endpoints enforce 100 requests per 15 minutes per IP.

6. BEGINNER-FRIENDLY CODE ARCHITECTURE EXPLANATION
--------------------------------------------------------------------------------

Q1: Why do we separate the 'app.ts' file from 'server.ts'?
A1: In 'app.ts', we configure Express (routes, middleware, and parsers). In 'server.ts',
    we start the network listener (`server.listen(5000)`). By keeping them separate,
    our automated test suite (Supertest) can import `app` and test HTTP requests
    directly in-memory without needing to bind to an actual network port.

Q2: Why use a 32-byte tracking token instead of a regular ID like #1001 for customers?
A2: If we used `/track/1001`, an attacker could change the URL to `/track/1002` and read
    another customer's confidential support conversations. A 32-byte cryptographic
    token has $2^{256}$ possibilities, making guessing or brute-forcing mathematically
    impossible.

Q3: What is the purpose of the 'asyncHandler' utility?
A3: In Express 4, if an `async` function throws an error (for example, when a status
    transition is invalid), Express does not automatically catch it unless you wrap
    it in a try/catch or use `asyncHandler`. Without it, the server would hang or log
    an 'UnhandledPromiseRejection'. `asyncHandler` ensures every error safely flows
    into our centralized error handler.
